# 解説

```sh
node -e 'console.log(010 + 0b10 + 0o10 + 0x10)'
node -e 'console.log(parseInt("010") + parseInt("0b10") + parseInt("0o10") + parseInt("0x10"))'
```

このクイズで、なぜリテラルと `parseInt` で結果が変わるのかを解説します。

> 注意：1つ目のリテラル版は `010`（旧式8進数）を含むため、**非strictのスクリプト**（`node -e '...'`）でのみ動きます。strict / module では `SyntaxError` です。

---

## 1. リテラルとして足す → `34`

それぞれの数値リテラルの値は次の通りです。

| リテラル | 解釈 | 値 |
| --- | --- | --- |
| `010` | 旧式8進数 | `8` |
| `0b10` | 2進数 | `2` |
| `0o10` | 8進数 | `8` |
| `0x10` | 16進数 | `16` |

合計すると、

```text
8 + 2 + 8 + 16 = 34
```

```javascript
> 010 + 0b10 + 0o10 + 0x10
34
```

---

## 2. `parseInt` で足す → `26`

`parseInt(string)`（基数省略）は、文字列を頭から読んで「解釈できる数字の並び」だけを数値にします。`0x` 接頭辞だけは特別に16進数として自動認識しますが、`0b` / `0o` や旧式8進数は認識しません。

| 式 | 解釈 | 値 |
| --- | --- | --- |
| `parseInt("010")` | 10進数（現代のJSは自動8進しない） | `10` |
| `parseInt("0b10")` | `"0"` まで読んで `b` で停止 | `0` |
| `parseInt("0o10")` | `"0"` まで読んで `o` で停止 | `0` |
| `parseInt("0x10")` | `0x` 接頭辞を認識して16進数 | `16` |

合計すると、

```text
10 + 0 + 0 + 16 = 26
```

```javascript
> parseInt("010") + parseInt("0b10") + parseInt("0o10") + parseInt("0x10")
26
```

---

## 3. なぜ違うのか

* **リテラル** はソースコード上の表記として、`0b` / `0o` / `0x` / 旧式8進すべてを基数付きで解釈する
* **`parseInt`** は文字列を10進数前提で読み、`0x` だけ例外的に16進数と認識し、`0b` / `0o` は「`0` の後に未知の文字」とみなして途中で読むのをやめる

同じ見た目でも、評価される文脈（リテラルか文字列か）で結果が変わります。

---

## まとめ

1. リテラル版：`8 + 2 + 8 + 16 = 34`
2. `parseInt` 版：`10 + 0 + 0 + 16 = 26`
3. `parseInt` は `0x` だけ自動認識し、`0b` / `0o` / 旧式8進は認識しない
